## 2026-08-26 01:04 — ревью ox-alpha: чат заказов, отзывы, аватары

### Fixed
- Архивация переписки упала бы в проде на первой же строке: миграция создала
  `chat_messages_archive.archived_at` как NOT NULL **без** DEFAULT, а модель
  объявляет `server_default` — SQLAlchemy в таком случае значение в INSERT не
  шлёт. В тестах не видно (схема там поднимается через `create_all`, где
  дефолт есть), джоб ходит раз в минуту и молча писал бы в лог NOT NULL.
  Проверено на мигрированной базе. Лечение: миграция `h4a5b6c7d8e9` ставит
  DEFAULT now(), модель дополнительно получила клиентский `default` — чтобы
  вставка была корректной и на базе, где дефолта ещё нет.
- Порядок архивной переписки. Сообщения на перенос выбирались без `ORDER BY`,
  а Postgres без него порядок строк не обещает: обновлённая строка (продавцу
  проставляется `tg_message_id`) переезжает в конец кучи и уезжает в архив
  последней. История сортируется по id — и переписка перемешивалась. Тест
  воспроизводит: без правки первое сообщение оказывалось последним. Заодно
  id при переносе сохраняется — у архивной таблицы своя последовательность,
  и сортировка по id опиралась бы на два независимых счётчика.
- Экранирование в пуше о новом отзыве (`services/reviews.py`): название товара
  и текст отзыва уходили продавцу в hub-бот с `parse_mode=HTML` как есть.
  Один «<» в отзыве покупателя — и Telegram отбивает сообщение, продавец про
  отзыв не узнаёт. Тот же класс, что и фикс `484802f`.
- Экранирование в пуше об отправке заказа (трек, ссылка, примечание продавца)
  — дефект был и раньше, но того же семейства; покупатель терял уведомление
  о доставке из-за «<» в примечании.
- Гонка ленивой докачки аватара: `bot_avatars.bot_id` уникален, а два
  одновременно открывших витрину покупателя вставляли строку оба — второй
  получал 500 на витрине. Теперь проигравший просто перечитывает чужую строку.

### Changed
- Индекс `order_chats.status` (миграция `h4a5b6c7d8e9`): джобы закрытия и
  архивации чатов ходят по статусу раз в минуту — без индекса это seq scan
  всей таблицы чатов, растущий вместе с числом заказов.
- «Мои покупки» тянули состав каждого заказа отдельным запросом (до 50 на
  ответ), а экран с этого инкремента сам обновляется раз в 10 секунд —
  N+1 множился на опрос. Состав всех заказов забирается одним запросом, как
  уже сделано в кабинете продавца.
- Rate limit чата чистит протухшие счётчики: ключей копилось столько же,
  сколько чатов за время жизни процесса, а окно живёт пять минут.

## 2026-08-25 00:19 — чат заказа: продавец ↔ покупатель, с авто-блокировкой

Обсудить заказ было негде: недопонимание по срокам и деталям кончалось
отменой. Теперь у каждого оплаченного заказа есть relay-чат, жёстко
привязанный к order_id: продавец пишет из кабинета, покупатель — прямо
в диалоге с ботом магазина. Стороны анонимны друг для друга, окно
обсуждения закрывается само.

### Added
- `backend/app/models/chat.py`: `order_chats` (1 заказ = 1 чат, статусный
  задел `active | locked_by_timeout | archived`), `chat_messages`,
  `chat_messages_archive`; в `orders` — метка доставки `delivered_at`.
- Миграция `c4d5e6f7a8b9` с бэкфиллом `delivered_at = paid_at` у уже
  доставленных; up → down → up проверены на пустой базе.
- `backend/app/services/chat.py` — ядро: открытость считается на каждом
  POST из `delivered_at + 72ч` (настройка `chat_window_hours`); rate limit
  2 с между сообщениями и ≤30 за 5 минут на участника (429); отмена заказа
  закрывает чат навсегда (read-only, история доступна); джобы
  `lock_expired_chats`/`archive_old_chats` в цикле каждые 60 с (`main.py`),
  архивация переносит сообщения в холодную таблицу через 30 дней после
  блокировки, чтение прозрачно объединяет обе таблицы.
- API продавца: `GET|POST /api/seller/bots/{bot_id}/orders/{id}/chat[…]`.
  Чужой order_id → 403 `foreign order`, неоплаченный → 403
  `chat_not_available`, закрытое окно → 403 `chat_locked`, лимит → 429.
  Те же пути у покупателя (`/api/store/{bot_id}/…`) с проверкой владения

## 2026-08-24 22:18 — вывод без самоподтверждения «я нажал /start»

Кнопка «Готово, я нажал /start» просила продавца подтвердить за систему то,
что система проверить не может: в API Crypto Pay нет метода, отвечающего,
открыт ли @CryptoBot у пользователя. Ошибиться можно было в обе стороны —
