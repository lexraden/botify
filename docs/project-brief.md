# Telegram Bot + Mini App Marketplace — проектный бриф

## Контекст для Claude Code

Ты помогаешь собрать MVP платформы на базе Telegram: бот + Mini App (WebApp), который объединяет функции лид-магнита, CRM и мини-маркетплейса. Ниже — полное описание идеи, архитектуры и порядка работы. Прочитай весь документ перед тем, как предлагать структуру проекта или писать код.

---

## 1. Что мы строим

Платформа для продажи товаров и услуг через Telegram, состоящая из:

1. **Telegram-бот** — точка входа для пользователей
2. **Telegram Mini App (WebApp)** — витрина с каталогом, открывается по кнопке внутри бота
3. **Backend + БД** — хранит пользователей, продукты, заказы, обрабатывает оплату
4. **Админ-панель** (может быть частью Mini App с проверкой роли) — для добавления товаров/услуг, обработки заказов

### Ключевые функции бота
- Приём заявок в закрытый канал/группу с авто-approve (Telegram join request handling)
- Сбор базы подписчиков: каждый, кто написал боту, попадает в БД (telegram_id, username, дата первого контакта, источник/UTM)
- Рассылки по базе (с учётом лимитов Telegram Bot API — не спамить)
- Кнопка запуска Mini App

### Ключевые функции Mini App
Два раздела с разным UX:

**Товары (Products)** — простой e-commerce флоу как в фастфуд-приложениях:
- Сетка товаров → карточка товара → добавление в корзину → checkout
- Поддержка физических и digital-товаров (digital — доставка ссылки/файла после оплаты)

**Услуги (Services)** — гайды, консультации и т.п.:
- Каталог с описанием, покупка = разовая оплата
- После оплаты — выдача доступа (файл, ссылка, приглашение в закрытый чат)

### Оплата (MVP)
- Только крипта на старте, без юрлица
- Используем **Crypto Pay API от @CryptoBot** (pay.crypt.bot), НЕ свой кошелёк с ручным мониторингом блокчейна
- Флоу: `createInvoice` при оформлении заказа → webhook `invoice_paid` → уведомление продавцу и покупателю в боте → `transfer` API отправляет продавцу его долю (минус комиссия платформы, например 3-5%) — либо сразу, либо пачкой (например раз в день)
- **Без внутреннего баланса на нашей стороне на старте.** Баланс/накопление на нашей платформе добавим позже, когда понадобятся споры/возвраты

**ВАЖНО — как именно работает выплата продавцу (уточнённая механика):**
Метод `transfer` в Crypto Pay API отправляет средства не на произвольный крипто-адрес, а на Telegram `user_id`, и получатель обязательно должен был хотя бы раз запустить @CryptoBot (нажать /start). Прямой отправки на адрес кошелька, который продавец вводит текстом, через этот метод НЕТ.

Из этого следует финальная схема:
1. При регистрации продавца в Mini App НЕ спрашиваем у него крипто-адрес — вместо этого получаем его Telegram user_id (это уже есть, т.к. продавец авторизован через Telegram)
2. Как часть онбординга продавца — проверяем/просим его один раз написать /start боту @CryptoBot
3. `transfer` кладёт его долю от продажи прямо на баланс продавца **внутри @CryptoBot** (это баланс CryptoBot, не наш внутренний баланс на платформе)
4. Дальше продавец сам, из интерфейса @CryptoBot, выводит средства на любой удобный ему внешний кошелёк — это уже не наша забота и не наш риск (мы не храним и не пересылаем на произвольные адреса)

Это и есть "упрощение" без внутреннего баланса на нашей стороне — просто выплата идёт через Telegram-аккаунт продавца, а не через адрес, который он бы вводил руками.

- В будущем: банковские карты, Apple/Samsung/Google Pay — потребует юрлица и провайдера типа Telr/PayTabs/Network International (UAE)

### Постпродажный флоу
1. Покупатель оплачивает → invoice_paid webhook
2. Бот шлёт продавцу сообщение: "Ваш товар купили, заказ #123"
3. Продавец открывает заказ в Mini App / боте → вводит трек-номер / ссылку / координаты / файл
4. Бот пересылает эти данные покупателю
5. Платформа переводит продавцу его долю через Crypto Pay `transfer`

### Роли пользователей
- **Покупатель** — просматривает каталог, покупает
- **Продавец** — добавляет товары/услуги, обрабатывает заказы, получает выплаты
- **Админ (я)** — модерация, настройки комиссии, доступ ко всей платформе

## 3.5. Мультибот-архитектура (КРИТИЧЕСКИ ВАЖНО — влияет на всю структуру БД и бэкенда)

Это не "один бот для всех", а мультитенантная система с изоляцией баз пользователей по продавцам.

### Два уровня ботов

1. **Hub-бот (главный, мой)** — точка входа ТОЛЬКО для продавцов, не для покупателей
   - Здесь происходит регистрация продавца, онбординг (подключение выплат через @CryptoBot), подключение собственного бота продавца
   - База подписчиков этого бота = только продавцы (их отдельная выборка, никогда не смешивается с покупателями)

2. **Bot продавца (seller bot)** — отдельный Telegram-бот, который продавец создаёт САМ через @BotFather и подключает к платформе
   - Внутри этого бота его покупатели видят каталог именно этого продавца
   - База подписчиков этого бота = только те, кто написал именно этому боту (покупатели конкретного продавца)
   - Рассылки, статистика, сбор лидов — всё изолированно, продавец видит и управляет только своей базой

**Главный принцип изоляции данных: каждый бот собирает только своих юзеров.** Юзеры hub-бота (продавцы) никогда не пересекаются с юзерами seller-ботов (покупатели). Между собой базы разных продавцов тоже не пересекаются — продавец А не видит и не может рассылать по базе продавца Б.

### Процесс подключения бота продавцом (встраивается в онбординг, после Шага 3 "подключение выплат")

**Шаг 3.5: Подключение своего Telegram-бота**
1. В hub-боте/Mini App — экран с инструкцией (в стиле остальных онбординг-шагов: текст + скриншоты + deep-link):
   - "Открой @BotFather"
   - "Отправь команду /newbot"
   - "Придумай имя и username для бота"
   - "Скопируй токен, который тебе пришлёт @BotFather"
2. Продавец вставляет токен в форму в hub-боте/Mini App
3. Бэкенд валидирует токен — вызывает `getMe` к Telegram Bot API; если ответ успешный, токен рабочий и принадлежит реальному боту
4. Токен **шифруется** и сохраняется в БД (это фактически полный доступ к чужому боту — обязательно encryption at rest, никогда не хранить как plaintext)
5. Платформа программно регистрирует webhook на этот бот: `/webhook/seller/{seller_id}` — с этого момента все апдейты (сообщения, join requests и т.д.) от юзеров этого бота летят на бэкенд платформы, но обрабатываются в контексте именно этого seller_id
6. Только после успешного подключения бота продавцу становится доступно добавление товаров/услуг

### Изменения в структуре БД

Новая таблица **`seller_bots`**:
- `seller_id` (FK на users/sellers)
- `bot_token` (зашифрован)
- `bot_username`
- `webhook_status` (pending/active/failed)
- `created_at`

Таблица **`users`** (или отдельные `hub_users` и `seller_end_users`) должна различать:
- Юзеров hub-бота (продавцы) — `source_bot: hub`
- Юзеров seller-ботов (покупатели конкретного продавца) — `source_bot: seller`, обязательно с полем `seller_id`, к которому они привязаны

Таблицы `products`, `orders` — тоже обязательно с `seller_id`, чтобы каталог, статистика и рассылки фильтровались строго по продавцу.

### Инфраструктурное требование: мультибот-раннер

Бэкенд должен уметь держать N ботов одновременно (не один хардкод-токен в `.env`, как в обычном одиночном боте), каждый на своём webhook-эндпоинте, и роутить входящие апдейты в общий движок логики (каталог/корзина/оплата), но с контекстом конкретного `seller_id`.

Mini App при этом остаётся одним и тем же кодом для всех — просто при открытии из конкретного seller-бота подгружает каталог, отфильтрованный по `seller_id` этого бота.

**Важно для Claude Code:** оплата всё равно идёт через ЕДИНЫЙ Crypto Pay app платформы (один API token на всю систему) — мультибот касается только приёма сообщений/сбора юзеров/рассылок, а не платёжного слоя. Заказы (`orders`) в БД просто хранят `seller_id`, чтобы `transfer` после оплаты уходил на правильного продавца.

**Честно про сложность:** это ощутимо увеличивает объём MVP по сравнению с архитектурой "один бот с ролями" — теперь нужна инфраструктура управления множеством ботов, шифрование токенов, раздельные вебхуки и строгая изоляция данных между продавцами. Закладывай на этот кусок больше времени, особенно на мультибот-раннер, а не на бизнес-логику каталога/оплаты, которая остаётся такой же, как обсуждали раньше.

### Онбординг с текстовыми инструкциями внутри UI

Везде, где от пользователя (особенно продавца или админа) требуется внешнее техническое действие — не просто написать это одной строкой, а сделать полноценный пошаговый onboarding-экран внутри Mini App: текст + скриншоты/картинки нужного экрана в Telegram, куда именно нажимать. Это касается минимум следующих шагов:

1. **Продавец: подключение выплат через @CryptoBot**
   - Шаг 1: открой @CryptoBot в Telegram (дать прямую deep-link кнопку "Открыть @CryptoBot")
   - Шаг 2: нажми /start (скриншот экрана бота)
   - Шаг 3: вернись в наше приложение и нажми "Проверить подключение"
   - Объяснить простыми словами: "сюда будут падать деньги с продаж, дальше сам выводишь на любой кошелёк"

2. **Продавец: подключение своего Telegram-бота** — см. подробный процесс в разделе "3.5. Мультибот-архитектура" ниже, шаг 3.5 онбординга

3. **Я как супер-админ: создание Crypto Pay приложения** (разовая настройка, но тоже стоит задокументировать как заметку в самом коде/README, не обязательно в UI)
   - Открыть @CryptoBot → Crypto Pay → My Apps → создать приложение → получить API token
   - Security → Transfers → Enable (без этого метод transfer не будет работать)

4. **Продавец: как оформить заказ / что делать после продажи** — короткий onboarding при первом добавлении товара: как прикреплять трек-номер/ссылку/файл к заказу после оплаты

Технически это может быть отдельный компонент типа `OnboardingStep` в Mini App: заголовок, картинка/скриншот, текст пояснения, кнопка перехода, кнопка "Готово/Проверить". Хранить состояние "прошёл ли онбординг" в БД у пользователя (`onboarding_completed: boolean` или пошаговый чек-лист), чтобы не показывать повторно.

## 8. Финальные уточнения по онбордингу и мультибот-структуре (после ревью готовых экранов)

> Этот раздел добавлен позже остальных и **имеет приоритет** над более ранними
> описаниями онбординга в разделе 3.5 (там онбординг шёл диалогом в чате бота).

### 8.1 Онбординг — переезд полностью в Mini App

Онбординг (Шаг 1 — подключение выплат через @CryptoBot, Шаг 2 — подключение своего
бота через @BotFather) реализуется полностью внутри Mini App, НЕ через чат-диалог
с ботом. Вёрстка берётся из готового дизайна (`docs/design/miniapp/`): progress bar,
alert-блок «уже есть бот», поле ввода токена с пометкой про шифрование.

Приветственное сообщение бота — одно, и под ним одна кнопка **«Открыть приложение»**
(`web_app`). По нажатию сразу стартует онбординг с Шага 1 или с того шага, на котором
продавец остановился (см. 8.2).

### 8.2 Персистентность прогресса онбординга — на бэкенде

Прогресс нельзя хранить только в клиентском состоянии: webview Telegram Mini App
пересоздаётся при долгом уходе в фон (переход в @BotFather/@CryptoBot и обратно,
особенно на iOS).

- Подтверждение шага сразу сохраняется в `sellers.onboarding_step`
  (`payment_pending → payment_done → bot_pending → bot_done`)
- При каждом открытии Mini App фронт первым делом запрашивает `GET /api/seller/me`
  и рендерит соответствующий экран, а не всегда первый шаг

### 8.3 Архитектура «один бот = один магазин»

Каждый подключённый бот продавца — отдельный, полностью изолированный магазин:
свой каталог, своя база покупателей, своя статистика, свои рассылки. Ничего не
шарится между ботами одного продавца.

**В БД:** `products`, `categories`, `orders`, `customers`, `mailings`, `channels`
привязаны к конкретной записи в `seller_bots` (колонка `bot_id`), а не только к
`seller_id`. Один продавец может иметь несколько ботов, у каждого — свой набор данных.

**Флоу после онбординга:**

1. Шаг 1 (выплаты) и Шаг 2 (первый бот) — как раньше
2. Продавец попадает в интерфейс магазина в контексте конкретного `bot_id`
3. Один бот → Mini App сразу открывает его магазин, без промежуточного экрана
4. Несколько ботов → сначала экран выбора магазина (список ботов), тап → магазин
5. Внутри магазина есть выход обратно к списку, чтобы переключаться без онбординга

**Проверка изоляции** покрыта тестами `backend/tests/test_shop_isolation.py`:
каталоги, заказы, покупатели и рассылки двух магазинов одного продавца не
пересекаются, а чужой магазин недоступен (404).
