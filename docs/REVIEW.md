## [ ] Прод: аватар магазина, тема и язык — живая проверка

**Контекст:** инкремент добавил аватар бота в шапке витрины (байты в БД,
раздача по токен-адресу), переключатели темы и языка RU/EN в профиле
покупателя с переводом всего Mini App. Тесты зелёные (pytest 157, vitest 56),
но из локальной среды недоступно:

1. Реальная загрузка аватара из Telegram: подключить нового бота → аватар
   появляется в шапке витрины; старый магазин без аватара подтягивает его
   лениво при первом открытии витрины покупателем.
2. Поведение темы внутри клиентов Telegram: переключатель 🌙/☀️ в профиле,
   дефолт «как в клиенте» (в тёмном клиенте витрина тёмная до первого рендера).
3. Переключение языка на лету: профиль EN → вся витрина/кабинет/онбординг
   английские, даты и суммы в нужной локали. Пуши бота остаются русскими —
   так и задумано.

**Известное ограничение:** смена картинки в @BotFather подхватывается только
при переподключении бота в кабинете (аватар качается один раз при connect +
лениво, если его ещё нет). Обновление по кнопке — отдельно, если понадобится.

## [ ] Прод: фото в чате заказа — живая проверка доставки

**Контекст:** в relay-чате появилась отправка фото (продавец — из кабинета через
«+», покупатель — фото в диалог с ботом магазина). Логика покрыта тестами
(pytest + vitest), но реальный Telegram из локальной среды недоступен: доставку
`send_photo` покупателю и приём фото от покупателя проверяет только деплой.

**Что сделать после деплоя:**

1. Кабинет → чат заказа → «+» → выбрать JPEG → покупателю приходит фото от бота
   магазина («💬 Заказ #N» + подпись).
2. Покупатель отправляет боту магазина фото без подписи и с подписью → оба
   видны в кабинете картинкой; пуш продавцу содержит 📷.
3. Реплай покупателя на фото продавца адресует именно тот заказ.
4. Фото больше 5 МБ у покупателя отбивается текстом про лимит.

## [ ] Прод: включить бэкапы Postgres

В коде бэкапов нет и быть не должно — это настройка Railway. Перед показом
первым юзерам проверить в Railway → Postgres, что включены ежедневные бэкапы
(в идеале point-in-time recovery). Без этого сбой инстанса = потеря всех
заказов, выплат и переписки.

## [ ] Детекция отозванного токена бота

**Что есть:** вебхуки ставятся один раз на старте приложения; статус видно
продавцу (`/mybots`, кабинет). Если продавец удаляет токен у BotFather,
Telegram снимает вебхук сам, у нас `webhook_status` остаётся «active» —
сообщения покупателей пропадают молча, продавец не узнает.

**Что сделать:** фоновая задача (раз в час достаточно): `get_me` по каждому
активному боту; 401/404 → `webhook_status = "failed"` + пуш продавцу в hub
«токен отозван, подключи бота заново» (ссылка на онбординг).

## [ ] Напоминание по зависшим manual-заказам

Заказ оплачен, `delivery_type: manual`, продавец молчит — сейчас это тупик:
покупателю написано «продавец готовит заказ», чат заказа не закрывается
никогда (72-часовое окно считается только от `delivered_at`), напоминаний
нет. Минимальный фикс: фоновая задача пушит продавцу в hub «заказ #N висит
без отправки N часов». Авто-отмена с возвратом денег — отдельно и позже
(рефанд через Crypto Pay требует отдельной проработки).

## [ ] Восстановление рассылок из статуса sending

Если процесс умрёт посреди отправки рассылки, она навсегда остаётся
`sending`: цикл её больше не подхватывает, в кабинете выглядит зависшей.
Мелкий фикс в `app/services/mailing.py`: при очередном тике рассылки в
статусе `sending` старше ~10 минут переводить в `pending` (дозаправка) или
помечать failed с кнопкой повторной отправки.

## [x] ~~Прод: застрявшие пачки выплат с SPEND_ID_ALREADY_USED~~

**Закрыто 2026-08-25:** выполнено в проде по инструкции — пострадавшие
пачки найдены и удалены.

**Контекст:** миграция `f9e8d7c6b5a4` добавила `payout_batches.spend_id` —
случайный токен вместо `batch-{id}` (тот ломался после сброса базы: нумерация
начиналась заново, и Crypto Pay отвечал SPEND_ID_ALREADY_USED на уже занятый id).
Миграция бэкфиллит старые строки значением `batch-{id}` — это правильно для
нормальных пачек, но у пачек, которые упали **именно с этой ошибкой**, бэкфилл
возвращает им тот самый уже занятый spend_id. Такая пачка будет падать вечно:
деньги по ней не ушли, но Crypto Pay считает идемпотентность-ключ исчерпанным.

**Что сделать после деплоя (Railway → Postgres):**

1. Найти пострадавшие пачки:

```sql
SELECT id, bot_id, amount, status, last_error
FROM payout_batches
WHERE status IN ('pending', 'failed')
  AND last_error LIKE '%SPEND_ID_ALREADY_USED%';
```

2. Для каждой найденной — удалить пачку. Доли продавца отвяжутся автоматически
   (`payouts.batch_id` имеет FK `ON DELETE SET NULL`), останутся `pending`,
   и следующее нажатие «Вывести» соберёт из них новую пачку с чистым случайным
   токеном — деньги дойдут без ручных переводов:

```sql
DELETE FROM payout_batches WHERE id = <id из шага 1>;
```

3. Продавцу, если он уже видел ошибку, можно написать, что выплата уйдёт
   повторным «Вывести» — сумма на месте.

**Не делать:** не помечать такие пачки sent вручную — в этом сценарии перевод
реально не уходил, отметка «sent» спишет баланс без выплаты.

Проверено локально: миграция up/down/up на SQLite, бэкфилл даёт `batch-{id}`,
pytest 121 passed. На живом Postgres миграцию прогонит деплой.
