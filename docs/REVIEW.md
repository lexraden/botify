## [x] ~~Прод: миграция `c4d5e6f7a8b9` переиспользует id из аварии 24.08~~

**Закрыто 2026-08-26:** прогнано локально на базе в состоянии прода. Риск был
в том, что старый штамп заставит alembic *молча* пропустить миграцию — этого
не происходит: деплой падает громко и с точным текстом. Ниже — что проверено
и рунбук на случай, если всё же всплывёт.

**Контекст:** ровно этот revision id уже был у миграции, которая уехала в прод
из ветки `ox-alpha`, а потом исчезла из репозитория вместе с откатом ветки.
Прод тогда лёг с `Can't locate revision identified by 'c4d5e6f7a8b9'`; лечили
полным сбросом схемы (`DROP SCHEMA public CASCADE`), вместе с ним ушла и
таблица `alembic_version` со старым штампом.

**Проверено (Postgres 16, база в состоянии прода — ревизия `a7b8c9d0e1f2`, с
данными: продавец, магазин, 5 заказов во всех статусах, выплаты, фото товара):**

1. `alembic upgrade head` доходит до `h4a5b6c7d8e9`, все шесть новых миграций
   применяются на непустой базе.
2. Бэкфилл `orders.delivered_at`: у обоих доставленных проставлен и равен
   `paid_at`, у недоставленных остался NULL.
3. Данные целы: заказы, выплаты, товары на месте, `products.image_url`
   не пострадал.
4. Откат `downgrade a7b8c9d0e1f2` и повторный `upgrade head` — чисто, данные
   на месте (путь отката деплоя рабочий).
5. Джоб архивации чатов прогнан **на схеме, построенной alembic**, а не через
   `create_all`: 4 сообщения перенеслись, `archived_at` заполнен, порядок
   переписки и id сохранены. Это то место, где прятался баг с NOT NULL.

**Если старый штамп всё же где-то уцелел** (проверено симуляцией):
деплой падает на `d8e9f0a1b2c3` с

```
sqlalchemy.exc.ProgrammingError: (psycopg2.errors.UndefinedTable)
relation "order_chats" does not exist
```

(не `DuplicateTable`, как предполагалось раньше — alembic пропускает
пропущенную ревизию, и следующая миграция не находит её таблиц). Лечение —
одна строка, вернуть штамп на реальное состояние схемы и накатить заново:

```sql
UPDATE alembic_version SET version_num = 'a7b8c9d0e1f2';
```

затем обычный `alembic upgrade head`. Проверено: после этого цепочка доходит
до `h4a5b6c7d8e9`, все четыре таблицы чата создаются. Сносить схему не нужно.

**Чего проверить было нельзя:** содержимое `alembic_version` на живом проде —
Railway из контейнера недоступен. Отдельной сверки это не требует: неверный
штамп не проходит молча, деплой упадёт с текстом выше. Если хочется
убедиться заранее — `SELECT * FROM alembic_version;` в Railway → Postgres,
ожидается `a7b8c9d0e1f2` (или `g2b3c4d5e6f7`, если прод уже собирался с
`ox-alpha`).

**Правило прежнее:** уже применённые миграции не переименовываются и не
удаляются; любая правка — новой миграцией сверху.

## [ ] Аватар магазина из Telegram, похоже, не читается в принципе — решение за владельцем

**Симптом (владелец, 26.08):** картинка боту выставлена через @BotFather, в
шапке витрины её нет. Функция не работает в проде.

**Разбор:** `app/services/bot_avatars.py` зовёт `get_chat(telegram_bot_id)` —
бот спрашивает Telegram про самого себя. `getChat` для приватного чата отдаёт
данные, только если пользователь с ботом уже взаимодействовал, а сам себе бот
написать не может: ожидаемый ответ — `Bad Request: chat not found`. Метода,
который вернул бы боту его собственную аватарку, в Bot API нет вовсе:
`getMyName`, `getMyDescription`, `getMyCommands` есть, `getMyPhoto` — нет,
картинка бота живёт только в @BotFather. Тот же сюжет, что с Crypto Pay и
проверкой «нажал ли продавец Start».

**Не подтверждено:** из контейнера `api.telegram.org` и `core.telegram.org`
закрыты прокси, живого токена нет — дословный ответ Telegram не получен.
Решающая проверка в одну строку: в логах Railway грепнуть
`Не удалось скачать аватар бота` — там лежит точная ошибка.

**Важно:** падение полностью беззвучное (`logger.exception` → `return None`,
бот попадает в `_failed_bots` и до рестарта больше не пробуется). Отсюда
ощущение «просто не работает» без единого сигнала.

**Предложено владельцу (ждёт решения):** функцию не убирать, а сменить
источник — логотип загружает продавец в кабинете. Вся инфраструктура уже есть
на фото товаров (магические байты, лимит 5 МБ, токен-адрес, `immutable`);
таблица `bot_avatars` остаётся, меняется только кто её наполняет. Тогда
удаляются `fetch_avatar_bytes`, телеграмный путь `refresh_bot_avatar`, вызов
из `bot_connect.py`, ленивая докачка в `store.py` и `_failed_bots`. Запасной
вариант прежний: нет логотипа — буква юзернейма.

**Пока не решено — не «чинить» обновление аватара по кнопке:** обновлять
нечего, источник недоступен.

## [ ] Прод: включить бэкапы Postgres

В коде бэкапов нет и быть не должно — это настройка Railway. Перед показом
первым юзерам проверить в Railway → Postgres, что включены ежедневные бэкапы
(в идеале point-in-time recovery). Без этого сбой инстанса = потеря всех
заказов, выплат и переписки.

## [ ] Детекция отозванного токена бота

**Что есть:** вебхуки ставятся один раз на старте приложения; статус видно
продавцу (`/mybots`, кабинет). Если продавец удаляет токен у BotFather,
Telegram снимает вебхук сам, у нас `webhook_status` остаётся «active» —
сообщения покупателей пропадают молча, продавец не узнает.

**Что сделать:** фоновая задача (раз в час достаточно): `get_me` по каждому
активному боту; 401/404 → `webhook_status = "failed"` + пуш продавцу в hub
«токен отозван, подключи бота заново» (ссылка на онбординг).

## [ ] Напоминание по зависшим manual-заказам

Заказ оплачен, `delivery_type: manual`, продавец молчит — сейчас это тупик:
покупателю написано «продавец готовит заказ», чат заказа не закрывается

нет. Минимальный фикс: фоновая задача пушит продавцу в hub «заказ #N висит
без отправки N часов». Авто-отмена с возвратом денег — отдельно и позже
(рефанд через Crypto Pay требует отдельной проработки).

## [ ] Восстановление рассылок из статуса sending

Если процесс умрёт посреди отправки рассылки, она навсегда остаётся
`sending`: цикл её больше не подхватывает, в кабинете выглядит зависшей.

статусе `sending` старше ~10 минут переводить в `pending` (дозаправка) или
помечать failed с кнопкой повторной отправки.

## [x] ~~Прод: застрявшие пачки выплат с SPEND_ID_ALREADY_USED~~

**Закрыто 2026-08-25:** выполнено в проде по инструкции — пострадавшие
пачки найдены и удалены.

**Контекст:** миграция `f9e8d7c6b5a4` добавила `payout_batches.spend_id` —
случайный токен вместо `batch-{id}` (тот ломался после сброса базы: нумерация
начиналась заново, и Crypto Pay отвечал SPEND_ID_ALREADY_USED на уже занятый id).
Миграция бэкфиллит старые строки значением `batch-{id}` — это правильно для
нормальных пачек, но у пачек, которые упали **именно с этой ошибкой**, бэкфилл
возвращает им тот самый уже занятый spend_id. Такая пачка будет падать вечно:
деньги по ней не ушли, но Crypto Pay считает идемпотентность-ключ исчерпанным.

**Что сделать после деплоя (Railway → Postgres):**

1. Найти пострадавшие пачки:

```sql
SELECT id, bot_id, amount, status, last_error
FROM payout_batches
WHERE status IN ('pending', 'failed')
  AND last_error LIKE '%SPEND_ID_ALREADY_USED%';
```

2. Для каждой найденной — удалить пачку. Доли продавца отвяжутся автоматически
   (`payouts.batch_id` имеет FK `ON DELETE SET NULL`), останутся `pending`,
   и следующее нажатие «Вывести» соберёт из них новую пачку с чистым случайным
   токеном — деньги дойдут без ручных переводов:

```sql
DELETE FROM payout_batches WHERE id = <id из шага 1>;
```

3. Продавцу, если он уже видел ошибку, можно написать, что выплата уйдёт
   повторным «Вывести» — сумма на месте.

**Не делать:** не помечать такие пачки sent вручную — в этом сценарии перевод
реально не уходил, отметка «sent» спишет баланс без выплаты.

Проверено локально: миграция up/down/up на SQLite, бэкфилл даёт `batch-{id}`,
pytest 121 passed. На живом Postgres миграцию прогонит деплой.
