# GLM.md — как работать с Claude Code в этом проекте если ты модель GLM

Адаптировано под нашу среду: сессии идут через **Claude Code CLI** (терминал)
локально на твоей машине, подключение к **OpenRouter** через
`ANTHROPIC_BASE_URL`, модель — **`z-ai/glm-5.3-flash`** (платная).
Репозиторий находится прямо на диске, изменения сохраняются.

## Правило номер ноль: экономия контекста не в ущерб качеству

Токены экономятся на **лишнем контексте**, а не на проверках. Что не режется
никогда:

- тесты прогоняются до пуша, а не «должно работать»;
- миграция проверяется в обе стороны (up → down → up) на пустой базе;
- «проверено» пишется только про то, что реально проверено — прод за
  владельцем проекта;
- задача доделывается целиком; если часть заблокирована — это проговаривается,
  а не тихо выпадает из объёма.

Если экономия и качество конфликтуют — выигрывает качество, а сессия просто
начинается заново.

## Главные правила

1. **Новая задача — новая сессия.** Закончил с оплатой, переходишь к загрузке
   фото товаров — начинай новый чат, не продолжай в старом. Иначе контекст,
   который уже не нужен (файлы платёжного слоя, логи, старые правки), тянется
   в каждый следующий запрос.

2. **Коммить и пушить — обязательно.** Локально ничего не пропадает, но
   без коммитов теряется история и сложно откатываться. Перед перерывом или
   сменой задачи — коммит (и пуш, если есть remote).

3. **Называй файл точным путём** — `backend/app/payments/payouts.py`, а не
   «файл с выплатами». Один точный путь экономит несколько поисковых вызовов.
   Повторять путь в каждом сообщении не нужно: файл, который уже открывали
   в этой сессии, остаётся в контексте.

4. **Модель всегда одна: `z-ai/glm-5.3-flash`.** Контекст 1.3M токенов,
   выход до 131K — можно держать в сессии много файлов и генерировать крупные
   куски кода целиком. Модель дешёвая и быстрая — **не экономь на проверках,
   лучше лишний раз прогнать тесты. Для сложных задач сначала проси план,
   потом код.**

5. **Откат — точечный, а не переписыванием разговора.** Если я пошёл не туда
   в последних правках, скажи «откати последние изменения в таком-то файле» —
   я сделаю `git checkout` по конкретным путям, это дёшево и не трогает
   контекст.

## Специфика нашей среды (локальная разработка)

- **Всё сохраняется локально.** Репозиторий уже на диске, изменения
  переживают сессию. Но это не отменяет коммитов — без них нет истории
  и сложно откатываться.
- **PR только по явной просьбе.** Ветка — да, PR — нет, пока не попросишь.
- **Postgres должен быть запущен локально.** Если не запущен — подними его
  (`service postgresql start` или через Docker).
- **Прод-домен Railway** — доступен или нет, проверки прода за владельцем
  проекта; с моей стороны это должно называться «не проверено», если я не
  делал реальный запрос.
- **`webapp/dist` коммитится в репозиторий** — бэкенд раздаёт его сам. После
  правок фронта пересборка обязательна, иначе в проде останется старая витрина.

## Специфика проекта

- **Один блок задач = одна сессия.** «Протестить оплату» и «разобраться с фото
  товаров» — разные куски кода (payments/webhook vs upload/storage), между ними
  новая сессия.
- **Шумные прогоны — только с кратким итогом.** Большие выводы (полный лог
  тестов, широкий grep) я по умолчанию сокращаю до сути. Если нужен именно
  полный вывод — скажи явно об этом.
- **Шумные команды — с тихими флагами**, они уже зафиксированы ниже.

## Особенности модели `z-ai/glm-5.3-flash`

- **Огромный контекст: 1 310 720 токенов (~1.3M).** Это позволяет держать
  в сессии весь проект целиком — не нужно дробить задачи из-за окна контекста.
  Но всё равно не тащи лишнее: мусор в контексте замедляет ответы и размывает
  внимание.
- **Большой лимит на выход: до 131 072 токенов.** Можно генерировать целиком
  большие файлы (миграции, модули, тесты) без разбиения на куски. Если файл
  не влезает — это повод задуматься, не слишком ли он разросся.
- **Полная поддержка function calling.** Инструменты Claude Code (чтение
  файлов, bash, редактирование) работают штатно. Если что-то не вызывается —
  проверь, правильно ли переданы пути и аргументы.
- **Structured Outputs (JSON) — есть, но без жёсткой схемы.**
  `response_format` поддерживается, но валидации JSON-schema нет. Для
  надёжного парсинга лучше просить модель возвращать JSON и проверять его
  в коде самому.
- **Дёшево.** $0.075 за 1M входных и $0.25 за 1M выходных токенов (со скидкой
  50% у провайдеров Z.AI и NovitaAI). Кэш-чтение — $0.015 за 1M. Полноценная
  сессия кодинга стоит копейки — **не экономь на проверках, лучше лишний раз
  прогнать тесты.**
- **Быстрая.** Flash-версия оптимизирована под скорость. Можно итеративно
  править код мелкими шагами и сразу прогонять тесты.
- **Не рассуждает «вслух» так глубоко, как флагманы.** Для сложных задач
  (платёжный слой, схема БД) **сначала проси краткий план, потом код** — так
  результат будет качественнее.
- **Русский — рабочий, но не идеальный.** Модель лучше всего понимает
  английский и китайский. Если замечаешь странности в русских текстах —
  переформулируй запрос или попроси объяснить на английском.

## Команды проекта (тихие варианты)

Запускать именно в таком виде — они не забивают контекст выводом.

```bash
# Тесты (Postgres должен быть запущен локально)
cd backend && .venv/bin/python -m pytest -q

# Один файл/тест
cd backend && .venv/bin/python -m pytest -q tests/test_fulfillment.py

# Сборка витрины после правок во webapp (dist коммитится в репозиторий)
cd webapp && npm run build 2>&1 | tail -5

# Миграции: применить
cd backend && .venv/bin/python -m alembic upgrade head

# Локальный запуск бэкенда (без WEBHOOK_BASE_URL вебхуки не регистрируются)
cd backend && .venv/bin/uvicorn app.main:app --port 8088
```

Тестовая БД по умолчанию — `postgresql+asyncpg://botify:botify@localhost:5432/botify_test`
(переопределяется `TEST_DATABASE_URL`); схема поднимается через `create_all`,
alembic там не прогоняется.

**Проверка миграции перед пушем** — на отдельной пустой базе, а не на тестовой,
и обязательно в обе стороны:

```bash
su postgres -c "psql -c 'DROP DATABASE IF EXISTS botify_mig' -c 'CREATE DATABASE botify_mig OWNER botify'"
cd backend && DATABASE_URL=postgresql+asyncpg://botify:botify@localhost:5432/botify_mig \
  .venv/bin/python -m alembic upgrade head && \
  .venv/bin/python -m alembic downgrade -1 && \
  .venv/bin/python -m alembic upgrade head
```

## Что нужно знать про код

- Архитектура и решения: `docs/AUDIT.md`, бриф: `docs/project-brief.md`,
  краткая карта репозитория: `README.md`.
- **Ручные действия после деплоя и открытые вопросы: `docs/REVIEW.md`.**
  Читать при старте сессии; закрытый пункт вычёркивается с пометкой (дата, что сделано).
- **Один подключённый бот = один изолированный магазин.** Каталог, покупатели,
  заказы, рассылки и статистика фильтруются по `bot_id`, а не по продавцу.
  Любой новый ресурс магазина заводится с `bot_id` и живёт под
  `/api/seller/bots/{bot_id}/…`.
- **Токены seller-ботов не хранятся в открытом виде** — только Fernet
  (`app/security.py`). В логи и ответы API они не попадают.
- **Схема БД меняется только миграцией.** Alembic-autogenerate тут не
  используется (нужна живая БД с историей) — миграции пишутся руками, с
  `downgrade` и, если надо, с бэкфиллом данных.
- **Выплаты копятся по магазину, а не по заказу и не по продавцу**
  (`app/payments/payouts.py`): у каждого бота своя касса, у Crypto Pay свой
  минимум на transfer (ниже него — `AMOUNT_TOO_SMALL`). Порог —
  `MIN_PAYOUT_USDT`; сам transfer комиссии не берёт (проверено переводом).
- **С продавца — только наши `commission_pct` от суммы заказа.** Комиссию
  Crypto Pay платформа платит из своей же комиссии: она пишется в
  `payouts.provider_fee` ради учёта маржи, но долю продавца не уменьшает.
  Берётся фактическая из вебхука, при её отсутствии — `CRYPTO_PAY_FEE_PCT`.
- **Суммы наружу — только через `app/money.py:fmt()`.** В БД `Numeric(18, 6)`,
  в тексте это «1.000000».
- Тексты бота и Mini App — на «ты», по-русски.
